## Q&A

**Q1 — `ocpy` is not on PyPI (release blocker).** `ocpy` is imported in 26
places across `bing/` and is a hard dependency, but it is hosted only at
`github.com/ocean-colour/ocpy`. Worse, a *different, unrelated* package named
`ocpy` already exists on PyPI (versions 0.5.x), so I deliberately did **not**
list `ocpy` in `dependencies` — doing so would make pip install the wrong
package. **Options:** (a) publish `ocean-colour/ocpy` to PyPI under a unique
name (e.g. `ocpy-ocean`) and add it as a dependency; or (b) keep documenting
the `pip install git+...` step (current approach). A true `pip install
bing-ocean` cannot work end-to-end until (a) is done. How would you like to
proceed?

**Q2 — Version number.** The package was at `0.0.dev0`; the README claimed
"2.0.0". I set the first PyPI release to **0.1.0** (conventional for a first
public release). If you'd rather align with the "2.0" line (the `bing_2.0`
paper effort), bump `bing/__init__.py:__version__` and I'll update the README.

**Q3 — Distribution vs. import name.** PyPI distribution name is `bing-ocean`
(the bare name `bing` is taken by Microsoft Bing); the import package stays
`bing`. Confirm `bing-ocean` is the desired PyPI name.

**Q4 — Copyright / org.** `LICENSE` and the old `setup.py` referenced
`AI-for-Ocean-Science`, but the live GitHub org is `ocean-colour`. I updated
all repository URLs to `ocean-colour` but left the `LICENSE` copyright holder
unchanged (legal/authorship decision). Update the copyright line if desired.

**Q5 — `correct_atmosphere` dependency.** `bing/fitting/l23.py` and
`bing/tests/tst_Ed.py` import `correct_atmosphere` (another `ocean-colour`
repo, not on PyPI) at module top level. Tests currently pass because it's
installed locally and in CI (installed from git). Consider making the import
lazy/optional so `import bing.fitting.l23` doesn't hard-fail without it.

**Q6 — `twine` not installed.** `twine check`/upload is the final release
step. Install with `pip install twine`, then
`python -m build && twine check dist/* && twine upload dist/*`.

### 2026-06-27 (Suppressed test figures from displaying on screen)

Executed Task 2.

**Diagnosis.** Searched the suite for figure-display calls. Found:
- `bing/tests/test_l23_fitting.py` — three tests
  (`test_raman_fitting_LM`, `test_raman_fitting_MCMC`, `test_Chl_fitting_MCMC`)
  call `bing_plot.show_fits(..., show=True)`, and `show_fits` calls
  `plt.show()` (plotting.py:286-287) when `show=True`. These were the real
  culprits popping up windows during a run.
- `bing/tests/test_raman.py` has two `plt.show()` calls, but both sit inside
  `if False:` blocks (dead code) so they never fire.

**Fix (two layers).**
1. Added `bing/tests/conftest.py` that calls
   `matplotlib.use("Agg", force=True)` at import time. pytest imports
   `conftest.py` before any test module, so the non-interactive Agg backend
   is in force before `pyplot` is first used. Under Agg, `plt.show()` is a
   no-op and nothing is rendered to a display — this guards all current and
   future tests (and runs headless on CI).
2. As defense-in-depth and to make intent explicit, flipped the three
   `show=True` → `show=False` in `test_l23_fitting.py`. The figures are still
   *built* (so the plotting code path is still exercised), just never shown.

**Verification.** Added a temporary test asserting
`matplotlib.get_backend().lower() == "agg"` under pytest — it passed,
confirming conftest takes effect. `test_raman.py` (16 tests) and
`test_raman_fitting_LM` both pass headless. Ran the LM plotting test with
`MPLBACKEND=` unset to prove the suppression comes from conftest, not the
environment. Removed the temporary test afterward.

**Learned.** The grep hits in `test_raman.py` were a red herring (`if False:`);
the actual display came from `show=True` plumbed through `show_fits`. Forcing
Agg in `conftest.py` is the robust, idiomatic fix; flipping the flags is the
explicit-intent complement.
